# ТЗ: альтернативный backend Ogg/Opus на Symphonia и libopus

Дата: 08.10.2026. Проект: LocalFlow / voiceAI.
Статус: задание на реализацию и проверку прототипа; не разрешение включать его в production по умолчанию.

## 1. Цель и границы

Добавить встроенное декодирование Ogg/Opus через готовый `symphonia-adapter-libopus`, без собственного Ogg demuxer, внешнего конвертера и зависимости от системного `PATH`. Получать PCM, пригодный для существующего STT: `Vec<f32>`, mono, 16 000 Гц.

Прототип должен доказать корректность аудио, воспроизводимость сборки и соблюдение правил распространения. Полная замена FFmpeg и исправление Windows M4A/AAC — отдельное задание: добавление Opus само по себе их не решает.

Исходные приложенные документы используются как аналитический материал. Их рекомендация поставлять FFmpeg не является поручением внедрить sidecar в рамках этого ТЗ.

Обязательный профиль v1:

- контейнер Ogg, кодек Opus, один логический аудиопоток;
- channel mapping family 0, один или два канала;
- локальные файлы `.ogg` и `.opus`, включая пути с Unicode и пробелами;
- последовательное декодирование целиком, без seek;
- работа на Windows x64, macOS x64/arm64 и Linux x64.

За пределами v1: Opus в WebM/Matroska/MP4, raw Opus, multistream/multichannel, другие mapping families, chained Ogg, multiplexed Ogg, live streaming, PLC/восстановление потерянных пакетов, нормализация громкости, UI-настройка выбора backend. Такие входы должны завершаться явной ошибкой, а не частичным успешным результатом.

Нативная поддержка Vorbis, AAC-LC/ALAC, MP3, FLAC и AIFF может быть следующим этапом. Не включать её и не обещать соответствующий охват в рамках этого прототипа.

## 2. Проверенные основания и ограничения

Документация адаптера 0.3.0 указывает совместимость с Symphonia 0.6, регистрацию `OpusDecoder` в собственном codec registry и возможность собрать libopus в итоговый бинарник через `bundled`. Лицензия адаптера — MIT OR Apache-2.0. [Документация адаптера](https://docs.rs/symphonia-adapter-libopus/0.3.0/symphonia_adapter_libopus/).

В исходниках этой версии число каналов ограничено 1–2; pre-skip складывается с packet trim-start, после первого пакета обнуляется, а `reset()` сбрасывает декодер. Это основания для специальных тестов, а не доказательство ошибки полного pipeline. Многоканальный Opus готовый адаптер не обеспечивает. [Исходники адаптера](https://docs.rs/symphonia-adapter-libopus/0.3.0/src/symphonia_adapter_libopus/lib.rs.html).

Правила временной шкалы, pre-skip, end trimming и output gain проверять по стандарту Ogg/Opus; информационную частоту в заголовке не принимать за частоту временной шкалы. [RFC 7845](https://www.rfc-editor.org/rfc/rfc7845).

Наличие C-библиотеки и FFI означает, что решение не является полностью pure Rust. Декодирование внутри процесса также не предоставляет процессной изоляции sidecar.

## 4. Зависимости и сборка

1. Стартовая пара для проверки: `symphonia = 0.6.1`, `symphonia-adapter-libopus = 0.3.0`. Это кандидаты, а не подтверждение совместимости с проектом. До основной реализации проверить сборку на заявленном проектом Rust 1.88 и всех targets.
2. Ввести feature `audio-symphonia-opus`, не включённый в default. Все новые runtime-зависимости активируются только им.
3. Для Symphonia выключить default features и включить только необходимые для Ogg/Opus компоненты. Не использовать `all`; итоговый набор записать в отчёте.
4. Для адаптера явно включить `bundled`; проверить дерево features и реальное отсутствие зависимости от системной libopus. Все `symphonia-*` должны принадлежать совместимой линии версий.
5. Зафиксировать транзитивные зависимости в lockfile; определить фактическую версию и источник C libopus, C toolchain и дополнительные build-инструменты. Не предполагать, что cargo-лицензионная проверка видит vendored C-код.
6. Проверить release-сборки для `x86_64-pc-windows-msvc`, `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`. Кросс-компиляция macOS x64 не заменяет проверку запуска этого бинарника.
7. В случае несовместимости не повышать MSRV и не менять базовый release toolchain молча: оформить блокер с вариантами совместимой пары или согласуемого обновления.

## 5. Выбор backend и обратимость

Без feature сохраняется существующий маршрут. С feature экспериментальный режим выбирается явной внутренней настройкой/параметром тестового запуска; сохранять публичные сигнатуры через обёртку при необходимости.

В экспериментальном режиме WAV продолжает использовать существующую ветку, Ogg/Opus — новый backend. Для других форматов можно сохранить явно выделенный legacy-маршрут. Неподдерживаемый или повреждённый Ogg нельзя автоматически передавать FFmpeg/afconvert: иначе тесты скроют ограничения кандидата. Результат диагностики должен однозначно показывать фактически выбранный backend.

Экспериментальный маршрут не запускает subprocess, не создаёт промежуточный WAV и не обращается к сети. Существующий converter не удаляется этим заданием. Обещание «без FFmpeg» относится только к новому маршруту Ogg/Opus.

## 6. Контракт декодирования

### 6.1. Определение формата

- Расширение и MIME — подсказки, не доказательство формата; окончательное решение принимает probe и проверка codec parameters.
- Использовать Ogg demuxer Symphonia и собственный registry с зарегистрированным `OpusDecoder`. Проверить, что factory действительно получает этот registry, а не только стандартный.
- До декодирования проверить доступность источника, непустой вход и лимиты; валидировать заголовки, channel mapping и supported profile. Валидные будущие/неподдерживаемые варианты отличать от повреждённых, где возможно.
- Пакеты чужих logical streams не смешивать с выбранным аудио. Второй поток/chain обнаруживать и отклонять; не возвращать только первую часть как полную запись.
- CRC, усечение страниц и некорректные размеры должны обнаруживаться. Если upstream не предоставляет нужной проверки, добавить ограниченный валидатор либо зафиксировать непрохождение gate; не писать новый demuxer.

### 6.2. PCM и временная шкала

- Рабочее декодирование Opus выполнять в 48 000 Гц. Проверить соответствие codec parameters этому режиму.
- Pre-skip и end trimming применяются ровно один раз. Зафиксировать, за какую операцию отвечает demuxer, адаптер и код LocalFlow; исключить двойное обрезание.
- Корректно обработать pre-skip больше первого пакета, короткую запись и конец внутри последнего пакета. Недопустимо молча отбрасывать остаток pre-skip.
- Header output gain должен применяться ровно один раз; дополнительный replay gain/нормализацию не вводить.
- Mono передавать без изменения каналов; stereo смешивать по правилу `(L + R) / 2`. Проверить порядок/представление каналов, не усреднять соседние значения planar-буфера как interleaved.
- Ресемплинг 48 → 16 кГц делать с сохранением состояния между пакетами, корректным flush и компенсацией задержки. Не менять общий микрофонный resampler.
- Для принимаемого прототипа требуется anti-aliasing. Использование текущего `resample_linear` допустимо только как промежуточный benchmark, не как доказательство качества финального backend.
- Выход — конечные `f32` без NaN/Inf. Не требовать диапазон строго ±1: gain и float-декодирование могут давать значения за его пределами; не вводить неоговорённый clipping.
- Длительность результата вычислять из количества реально возвращённых mono samples / 16 000; metadata duration использовать только как предварительную оценку.

Ошибка на любом этапе означает отсутствие PCM-результата для STT. Стратегия v1 строгая: повреждённые/неполные записи отклоняются, частичное восстановление не выдаётся за успешное декодирование.

## 7. Ресурсы, отмена и безопасность

- Путь к файлу читать через потоковый источник, не через дополнительную полную копию `fs::read`. Вход из уже имеющихся bytes может использовать cursor; не копировать его без необходимости.
- Сохранять текущий лимит upload 80 MiB. Общие byte/output/time-лимиты передавать в backend также из CLI и иных входных точек; не ограничиваться frontend.
- Ввести `DecodeOptions` с явными `max_input_bytes`, `max_output_samples`, deadline и cancellation token. Численные production-лимиты длительности/памяти согласовать отдельно; тестовые значения зафиксировать в fixtures/настройках прототипа.
- Проверять output budget до расширения результирующего вектора, размеры заголовков/пакетов — до больших выделений; использовать проверяемую арифметику и обработку ошибок выделения, где доступно.
- Учесть: итоговый `Vec<f32>` неизбежно растёт с длительностью; mono 16 кГц занимает около 230,4 MB за час. Пакетная обработка ограничивает промежуточные буферы, но не делает суммарную память постоянной.
- Отмену/deadline проверять между чтением, декодированием и ресемплингом пакетов; ограничивать количество работы без проверки. На тестовом корпусе отмена должна завершать задачу не позднее 1 секунды после запроса.
- Использовать отдельный токен файловой задачи: отмена не должна останавливать диктовку или другую независимую загрузку. `spawn_blocking` сам по себе не отменяет вычисления.
- Освобождать источники, PCM и upload staging после успеха, ошибки и отмены; для worker panic предусмотреть cleanup владельцем staging. Отдельно задокументировать ограничения cleanup при аварийном завершении процесса.
- Не логировать аудио, расшифровку, теги и полный пользовательский путь. Разрешены код ошибки, backend/version, codec/container, размер и ограниченные технические счётчики.
- Добавить fuzz/property-проверки заголовков и пакетного цикла; Rust panic не использовать как защиту от memory corruption в C/FFI.

## 8. Ошибки и интерфейс

Ввести стабильные различимые категории, совместимые с существующим форматом ошибок:

| Код                          | Смысл                                                     |
| ---------------------------- | --------------------------------------------------------- |
| `AUDIO_FORMAT_UNSUPPORTED`   | Неподдерживаемый контейнер/кодек/профиль                  |
| `AUDIO_CHANNELS_UNSUPPORTED` | Каналы или mapping не поддерживаются                      |

| `AUDIO_DECODE_TIMEOUT`       | Истёк deadline                                            |
| `AUDIO_CANCELLED`            | Пользователь отменил файловую задачу                      |
| `AUDIO_OUTPUT_INVALID`       | Пустой либо некорректный итоговый PCM                     |

Для нового backend не показывать предложение установить FFmpeg. Сообщение о неподдерживаемом профиле: «Этот вариант аудиофайла пока не поддерживается». Для повреждения: «Не удалось прочитать аудиофайл. Возможно, он повреждён».

Добавление `.opus` синхронизировать между UI, `AUDIO_EXTENSIONS`, CLI и backend. Не рекламировать поддержку `.opus` в обычной сборке без нового backend. Не выдавать общую поддержку OGG за поддержку любого кодека/профиля внутри него.

## 10. Тестовый корпус и критерии

Все fixtures должны иметь SHA-256, происхождение/право использования, manifest с профилем и ожидаемым результатом. Использовать синтетический сигнал и разрешённые обезличенные записи, не личные голосовые сообщения пользователя.

| Группа          | Обязательные случаи                                                                                 | Ожидаемый результат                                         |
| --------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Базовая         | Mono/stereo, тишина, речь, разные длительности пакетов, VBR                                         | Успешный PCM 16 кГц mono                                    |
| Границы         | Pre-skip 0/обычный/больше первого пакета; запись короче пакета; end trim                            | Точное число samples до resampling, без сдвига начала/конца |
| Временная шкала | Разные informational input rates, начальная granule position, gain 0/положительный/отрицательный    | Правильные длительность и амплитуда                         |
| Каналы/профили  | >2 каналов, иная mapping family, chained/multiplexed Ogg                                            | Явный отказ, без частичного успеха                          |
| Повреждение     | Усечение header/page/packet, неверный CRC, битые granules, большой metadata packet, случайные bytes | Ошибка, без panic/зависания/STT                             |
| Идентификация   | Подмена расширения/MIME, Ogg/Vorbis, WebM/Opus                                                      | Решение по содержимому, профиль v1 не расширяется случайно  |
| Ресурсы         | Длинная запись, input/output cap, deadline, отмена, параллельные задачи                             | Лимиты и cleanup, независимая отмена                        |
| Интеграция      | UI upload, CLI file/bytes, Unicode path, повторный запуск после ошибки                              | Один контракт, отсутствие утечек/остаточного состояния      |
| Регрессии       | Feature off; WAV; legacy форматы                                                                    | Сохранение поведения вне нового маршрута                    |

Reference-декодирование выполнять зафиксированной версией libopus/opusfile или FFmpeg в тестовой среде; инструменты создания fixtures не становятся runtime-зависимостью приложения. Сохранять команды, версии и expected PCM отдельно от реализации кандидата.

Приёмка сигнала:

- До resampling количество mono frames совпадает с reference точно; тесты начала/конца не допускают добавленной тишины или потери ожидаемого участка.
- При одинаковой версии libopus, gain и float-режиме максимальная абсолютная разница с reference не более `1e-5`; если target/SIMD требуют иной допуск, обосновать и утвердить его до принятия результата, не скрывая timing/gain ошибки выравниванием.
- После resampling число samples отличается от согласованного reference не более чем на один sample; задержка фильтра компенсирована по заранее определённому правилу.
- Отдельный unit-тест resampler: синус 10 кГц подавлен не менее чем на 40 dB относительно входного уровня при 48 → 16 кГц, после исключения согласованных переходных участков. Это инженерный порог ТЗ, не заявление о гарантии библиотек.
- Нет NaN/Inf, packet-boundary скачков, двойного gain/trim. Пустой результат не передаётся STT.

На каждой целевой ОС проверить установленную экспериментальную сборку в окружении без FFmpeg и системной libopus. Аудио-test должен реально выполниться, одной успешной компиляции недостаточно.

Измерить release decode time, peak RSS, размер бинарника/установщика и поведение отмены на фиксированных коротком и длинном файлах. Отчёт содержит hardware и baseline; выигрыш размера/скорости заранее не обещается. Порог производительности для production назначается после измерений.

## 11. Этапы и результаты

1. **Build spike и licensing review.** Проверить версии, MSRV, bundled linking и targets; представить дерево компонентов, ограничения и решение о допустимости экспериментальной поставки. При провале — отчёт о блокере до интеграции.
2. **Изолированный decoder.** Feature, registry, supported profile, PCM contract, базовые/reference-тесты. Сначала проверить pre-skip/end trim/gain; не строить UI вокруг непрошедшего кандидата.
3. **Ресурсы и интеграция.** Потоковый input, budgets, cancellation, staging cleanup, UI/CLI experimental route и структурированные ошибки.
4. **Проверка устойчивости и поставки.** Повреждённые fixtures, fuzz smoke, regression suite, CI target matrix, installer smoke, notices/SBOM и performance report.
5. **Решение по результатам.** Принять прототип, принять с явно согласованным сокращением профиля либо отклонить кандидат. Включение по умолчанию и расширение на M4A/AAC требуют отдельного решения/ТЗ.

Итоговые артефакты: изменения кода и lockfile; fixtures/manifest; CI-проверки; лицензионные материалы; отчёт с таблицей pass/fail и воспроизводимыми командами; перечень неподдерживаемых вариантов и инструкции включения/отключения.

## 12. Gate завершения

Прототип принят только если обязательный профиль проходит весь корпус, соблюдает budgets/cancellation, не вызывает внешние конвертеры на новом маршруте, работает в установленных сборках на всех targets и имеет проверенные материалы распространения.

Если готовый адаптер не проходит обязательные timing/gain/header-тесты, не объявлять интеграцию завершённой. Представить минимальный воспроизводимый пример и варианты: совместимое обновление upstream, отдельно согласованный локальный patch с pinned source либо смена кандидата. Собственная связка Ogg demuxer + libopus и реализация multistream не входят в это ТЗ автоматически.
